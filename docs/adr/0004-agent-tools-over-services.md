# Agent tools wrap services; the LLM never touches the database

The fund assistant's tools call the same service functions the dashboard routes call (`src/api/<domain>/service.ts`). The model never receives a database client, never composes SQL, and never writes a row directly — a tool call is a service call, so zod validation, admin guards, share-price snapshots, FIFO repayment, and `createdBy` attribution apply to agent writes exactly as to dashboard writes. A financial ledger is the worst place for an LLM to improvise writes; reusing the service layer makes every existing invariant un-bypassable by construction.

Every write is gated: tools marked `needsApproval` pause the run and surface a confirm card whose values come from a server-side preview built from DB reads — never from the model's own paraphrase. Telegram approvals are server-held (`AgentPausedApproval`, 10-minute TTL) because webhook callbacks are stateless. Role scoping happens at the tool-schema level (the Editor registry drops Adjustments and Share changes entirely) with a runtime double-check. Free text (names, notes) is treated as data: it round-trips verbatim and is never interpreted as instructions. Sanity caps (whole taka ৳1–1,00,00,000; dates ≤35 days future) sit in the tool layer above the service schemas.

Member notifications follow the same boundary: services emit one awaited, never-throwing event after a member-touching write (awaited because Vercel kills unawaited work), and `NotificationLog` dedupes and retries. TanStack AI drives the loop (GLM via an OpenAI-compatible endpoint); Telegram is a raw Bot API client behind a secret-token webhook with `update_id` replay dedupe.
